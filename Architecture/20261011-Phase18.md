### 1.4 Types

Used as earlier documents define them: `ClientRead<T>` and `Counters` (Phase 9 §2.2,
Phase 11 §1.4), `PlateRecord` (Phase 15 §1.4), `SettingsPage` and `ValueUnit`
(Phase 12 §1.4), `MarkerReading` and `MarkerCapability` (Phase 17 §1.4).

Defined here:

```
# What styling the guild label achieved. The fallback is today's behaviour: a
# readable label without an outline, never a missing label. SetFont returns a
# success bool, so "did not raise" is not the same as "applied" (section 2).
type LabelStyling = Outlined | PlainFallback(reason: string)

# Where the marker sits relative to the health bar's container. The anchor corners
# are fixed -- the marker's right edge against the container's left -- and the two
# offsets move it, in screen pixels at any scale (section 3).
type MarkerPlacement = {
    offsetX: integer,   # negative is further left of the plate
    offsetY: integer,   # positive is higher
    scale:   number
}

# Whether a QuestieDB read produced an answer at all. The distinction the Phase 17
# defect collapsed: an answer that is empty may be cached, a non-answer may not
# (section 5).
type BridgeReading<T> = Answered(value: T) | DidNotAnswer(reason: string)
```

- **`LabelStyling` has a `PlainFallback` arm because `SetFont` can refuse.** `GetFont`'s
  file is documented `Nilable = true` and `SetFont` requires a valid font asset, so a
  nil file must not be passed on; and `SetFont` reports refusal by return value rather
  than by raising.
- **`BridgeReading<T>` replaces rev 1's "fix all three the same way".** Audit finding 7
  showed that `copyIdList` cannot tell a getter that raised from a getter that answered
  `nil`, and that an NPC which genuinely starts no quests is the common case — so a
  blanket "do not cache a failure" would un-cache every guard, vendor and critter.
- **There is no `TooltipAnchoring` type any more.** §4 does not ship.

## 2. A black outline on guild names

### 2.1 Why the current code cannot just add a flag

Phase 15's label sizes itself with `SetTextHeight` on a font inherited from
`GameFontHighlightSmall` (`Features/Nameplates.lua:325-329`). `SetTextHeight` changes
the height and nothing else: there is no outline in it to turn on. The flag lives in
the third argument of `SetFont`, which means the font's **file name** has to be
supplied along with it — and the only way to know the file an inherited font object
uses is to ask for it.

**What the pool actually hands out** (`Features/Nameplates.lua:296-313`): a `Frame`
with a child font string at `frame.text`. The frame carries the height; the font
string carries the font. So the two calls go to two different objects, and rev 1's
signature — which invented a `FontStringFrame` and called `GetFont` on the frame —
would have raised `attempt to call method 'GetFont' (a nil value)` on the first plate
(§15, finding 2).

```
# Applies the outline, and the size, to one pooled guild label.
# pre:  label is a Frame from the guild pool, carrying a child font string at
#       label.text; points passed ConfigSchema
# post: label's height fits points, always, by the same SetTextHeight path Phase 15
#       shipped -- the size is applied before the outline is attempted and does not
#       depend on it.
#       Outlined when label.text:GetFont() answered a Plain, non-nil file AND
#       label.text:SetFont(file, points, "OUTLINE") RETURNED TRUE.
#       PlainFallback(reason) on any other path: the file read did not answer,
#       answered nil, SetFont raised, or SetFont returned false. The label then
#       keeps its Phase 15 sizing and is still readable -- the fallback is a label
#       without an outline, never a label without text. Noted once, counted
# raises: never
function style_guild_label(label: Frame, points: integer) -> LabelStyling
```

- **`SetFont` returns a success bool, and the contract reads it**
  (`SimpleFontStringAPIDocumentation.lua:514-517`). It also carries
  `RequiresValidFontAsset = true` and `SecretArguments = "AllowedWhenUntainted"`, so it
  can refuse — by gate, or because our execution is tainted — and a refusal returns
  `false` rather than raising. Treating "did not raise" as success is how a silently
  unstyled label would be reported as `Outlined`, which is the non-answer-as-answer
  defect §5 and §13 are about.
- **`GetFont`'s `fontFile` is documented `Nilable = true`** (`:130`), so nil is an
  answer the client is entitled to give, and `RequiresValidFontAsset` means passing it
  on would be refused. The fallback arm is load-bearing.
- **A fallback is never permanent, and rev 1's reason for it was wrong.** Rev 1 claimed
  `Absent` was the answer on a label that has not drawn yet; that was an untested
  assumption, and audit finding 3 is right to reject it — a font string inheriting
  `GameFontHighlightSmall` carries its font from creation. The reason for `ClientRead`
  is the documented nilability above, not drawing order. **And the styling sits inside
  `sizeGuildLabel`, which runs on every attach (`:356`) and on every font-size change
  via `FramePool.ForEach` (`:437`)** — so a one-off refusal is retried the next time
  that label is used, and finding 3's "newly tracked plates would permanently remain
  un-outlined" cannot happen.
- **The outline is not a setting** (D3). The guild line is deliberately faded to 70%
  alpha (`GUILD_LABEL_ALPHA`) so it reads as secondary, and an outline is what lets it
  stay legible at that alpha over a bright nameplate. Those two decisions belong
  together rather than as two switches a player has to find.
- **`"OUTLINE"` being an accepted flag is an in-game fact, not a documented one.** The
  flags argument is typed `TBFFlags` (`:511`) and **nothing in the export defines that
  type** — there is no enumeration of its values to check. Premise 66 asserts only that
  the argument and the success return exist; whether this client accepts `"OUTLINE"` is
  what §11.3 step 1 establishes, and T1 asserts the success return is what decides.
- **`THICKOUTLINE` is not used.** At `GUILD_FONT_MINIMUM` (6 points) a thick outline
  leaves almost no letter.

## 3. The marker's position

### 3.1 Two sliders, not a menu

Rule 1 forbids dropdowns: an option list is a function Blizzard calls, and Phase 12
§1.3 recorded that. So "choose the position" is expressed the way the combat panels'
position already is (Phase 12 §4) — **an anchor this design fixes, and two offsets the
player moves.**

| | Before (Phase 17 §4.4) | After |
|---|---|---|
| Anchor | marker `BOTTOM` → container `TOP` | marker `RIGHT` → container `LEFT` |
| Default | directly above the health bar | `QUEST_MARKER_OFFSET_X` (−4) px to its left, vertically centred |
| Controls | `markerOffsetY`, `markerScale` | `markerOffsetX`, `markerOffsetY`, `markerScale` |

```
# Places one plate's marker.
# pre:  the marker was acquired from the pool; plate.container resolved at attach
# post: the marker's RIGHT edge sits placement.offsetX, placement.offsetY from the
#       container's LEFT edge, in screen pixels at any scale because each offset is
#       passed as offset / scale (Phase 12 section 4's rule); the marker's scale is
#       placement.scale. Nothing is parented to, or written onto, the plate
# raises: never
function place_marker(marker: Frame, plate: PlateRecord, placement: MarkerPlacement)
```

- **The sliders move the marker around the plate's left side, and that is all they
  claim.** Rev 1 also claimed they could restore Phase 17's centred-above placement by
  setting the across-slider to 0, and **that was arithmetically false**: with the
  marker's right edge against the container's left edge, zero leaves the marker wholly
  outside the bar, about 68 px from where it used to be for a 120 px container, and the
  ±40 range cannot reach back (§15, finding 1). The claim, its assumption and its
  harness check are gone rather than patched, because the user asked for the marker to
  the *left* of the plate and that is what the anchor delivers.
- **Still the container, not `UnitFrame`.** Phase 14 made the bar's height a setting and
  the container is the frame that follows it (premise `PLATE-BAR-CONTAINER-HEIGHT`). The
  container's left edge is also where the bar's left edge actually is, which `UnitFrame`
  would not give.
- **The offsets are divided by the scale.** Otherwise "four pixels left" would mean six
  at 150% and three at 80%, which is the defect Phase 12 §4 fixed for the panels.
- **`markerOffsetY` is now measured from the bar's vertical centre, not its top**, so
  its range becomes symmetric (±40) and its label changes (§6). Rev 1's assumption that
  it "keeps its name and meaning" was wrong on the second half (§15, finding 15).
- **Both sliders call `refresh_markers`** (Phase 17 §4.4), so markers already drawn move
  as the slider does.
- **The guild label is below the bar and the marker is now beside it,** so the two
  decorations no longer compete for the same strip of screen.

## 4. Why the tooltip is not locked to the nameplate

D1 said to try the client's CVars first. That was the right order of investigation, and
it is now done — offline, against the export and the binary. **The route does not lead
where the request needs it to, for three independent reasons.** Any one of them would
be enough.

### 4.1 The CVars govern a different tooltip

`Enum.WorldCursorAnchorType` does have a `Nameplate` value, and
`GameTooltipDataMixin:SetWorldCursor` does handle it
(`Blizzard_GameTooltip/Mainline/GameTooltip.lua:987-1001`). But its first line is:

```lua
local tooltipData = C_TooltipInfo.GetWorldCursor();
```

That is the **world-cursor tooltip** — the soft-target and interact tooltip. It is not
the unit tooltip that `GameTooltip:SetUnit` fills for the unit you have targeted or are
hovering, and nothing on this path repositions that one. The request was for the
tooltip of the unit whose nameplate it should sit beside; rev 1 wrote §9 and §12 as
though the two were the same tooltip, and they are not (§15, finding 13).

### 4.2 The Gamepad UI already owns those CVars, and turns that tooltip off

`Blizzard_Gamepad/Core.lua:1-33`, in `SetupCVarsForInputMode`:

```lua
SetupTempCVar("SoftTargetNameplateEnemy", 0);
SetupTempCVar("SoftTargetNameplateInteract", 0);
SetupTempCVar("SoftTargetTooltipEnemy", 0);
SetupTempCVar("SoftTargetTooltipFriend", 0);
```

where `SetupTempCVar` is `C_CVar.SetTempCVar` when the gamepad is active and
`C_CVar.RemoveTempCVar` when it is not. This runs from `InputUtil.RegisterGamepadInit`
and is re-applied on every input-mode transition
(`InputUtil.RegisterForInterfaceTransitions`, `:68-70`).

So on the very UI this addon is built for, **Blizzard deliberately disables the
soft-target tooltip**, through a temp-CVar override layer, re-asserted whenever the
input mode changes. An addon writing those CVars is contending for state another system
owns and actively re-establishes — and `SetCVar` writes the persistent value while a
temp override is in force, so the likely result is a write that succeeds, reads back
correctly, and changes nothing. That is the worst available failure: silent.

It is also the answer to the one thing §11.4 was going to spike. **The CVars are
settable** — Blizzard's own Lua sets them, so the three `SetCVar` gates pass.
Settability was never the problem.

### 4.3 The positioning call is undocumented and appears once

The `Nameplate` branch positions the tooltip with:

```lua
self:SetOwner(parent, "ANCHOR_NONE");
self:SetObjectTooltipPosition();
```

Two things about this:

- **`parent` is `UIParent`, not a nameplate.** `GameEvent.HandleWorldCursorTooltipUpdate`
  calls `GameTooltip:SetWorldCursor(anchorType)` with no parent
  (`Blizzard_Game/Mainline/EventImplementation.lua:889-891`), and `SetWorldCursor`
  defaults `parent` to `UIParent` when it is nil. So the nameplate is never passed in;
  all placement is inside the second call.
- **`SetObjectTooltipPosition` occurs exactly once in the entire export** — that call
  site — **and has no documentation entry at all.** It is an undocumented C method, so
  whether it even exists on this client is unverified, and it takes no offset. The user
  asked for "a few pixels to the right, with the tooltip anchor far left and centre";
  this path offers no way to express any of that.

### 4.4 What the remaining routes cost

Neither is obviously right, and the choice is the user's.

| Route | What it gives | What it costs |
|---|---|---|
| **Post-hook `GameTooltip_SetDefaultAnchor`** and re-anchor when the tooltip's unit has a plate | Exactly the asked-for behaviour, offsets and all, in well under a day | Rule 4 is satisfied (a post-hook), but it means our `SetPoint` on Blizzard's `GameTooltip`. Blizzard's own comment on this file says reading old tooltip info "can taint if the tooltip was previously shown by a user addon" and that the consequence is **"the tooltip displaying no lines"** (`GameTooltip.lua:1003-1010`). An addon that re-anchors `GameTooltip` is precisely the condition that comment describes, and the symptom is a blank tooltip — the hardest kind to attribute, and the kind that cost Phase 16 and Phase 17 a detour each |
| **Our own tooltip frame**, parented to `UIParent`, filled from `C_TooltipInfo`/`Unit*` | No taint exposure at all (rule 6), full control of anchor and offset, and it can sit beside the plate without touching Blizzard's tooltip | A real feature rather than a setting: name, level, classification, guild, faction, health and status lines all drawn and kept current; and it will not match the game's tooltip exactly, so the two look different side by side. Several days, not an afternoon |

**Recommendation: the second.** This addon already parents every frame it owns to
`UIParent` and already renders tooltip content in `Features/NPCQuests.lua`, so the
machinery is familiar; and the first route buys a documented silent failure on the exact
path the pad cursor already walks (Phase 12 §20 recorded that DrinkBot's and
AutoPotion's tooltip scripts run inside `SelectButton`, GAPBugs01 §2.9's `currentButton`
carrier). But it is several days of work for a cosmetic win, so it should be its own
phase and the user's decision, not something smuggled into this one.

## 5. The Phase 17 defect that a relog fixed

The user reported the quest markers not working, then reported them working after
logging out and back in, with nothing else changed. That is a real defect and its cause
is a cache that keeps a failure.

`Core/QuestieDBBridge.lua`, as Phase 17 shipped it:

```lua
local ok, objectives = pcall(getter, questId)
if ok and ClientRead.Classify(objectives, "table") == ClientRead.PLAIN then
    ...extract...
end
-- unconditional:
state.targetsByQuest[questId] = out
```

So when the read **fails** — `pcall` raised, or the value came back something other
than a plain table — an empty list is cached for that quest **for the rest of the UI
load**. Nothing re-reads it: Phase 17 §2.4 says the cache is never invalidated because
QuestieDB's data is static, which is true of the data and false of a failed read of it.
A relog is the only thing that clears it, which is exactly the symptom reported.

### 5.1 The distinction, and why "fix all three the same way" was wrong

Rev 1 said all three cached reads have the same shape and all three are fixed the same
way. Audit finding 7 showed why that would have made things worse. `copyIdList`
(`:229-246`) returns `{}` for **four** different situations:

1. the getter is not a function;
2. `pcall` raised;
3. the value was not a plain table — which includes **`nil`, the answer QuestieDB gives
   for an NPC that starts no quests**;
4. the value was a plain, genuinely empty table.

Cases 3-with-nil and 4 are answers. Cases 1 and 2 are not. Treating all four as failures
would un-cache every guard, vendor and critter in the world and re-read QuestieDB on
every mouseover — the exact cache bypass Phase 17's audit finding 18 required caching
negative results to prevent.

So `copyIdList` reports which it was, and each caller decides:

```
# post: returns the id list, and whether the read ANSWERED. A getter that is absent
#       or raised did not answer. A getter that returned nil, or a plain empty
#       table, DID answer -- emptily -- because "this NPC starts no quests" is the
#       commonest true answer QuestieDB gives
# raises: never
function copy_id_list(
    entity: table,
    getterName: string,
    id: integer
) -> BridgeReading<List<integer>>
```

| Function | Cached on a non-answer before | After |
|---|---|---|
| `KillTargetsForQuest` | an empty list, permanently | nothing cached; empty returned, `readFailed` counted |
| `QuestsStartedBy` | an empty list, permanently | the same — **but an answered-empty list is still cached**, so the common case keeps its cache hit |
| `QuestFacts` | `false`, conflating "QuestieDB does not know this quest" with "the reads failed" | `false` only when the name read **answered** and the quest is genuinely absent |

**`QuestFacts` needs its own criterion** (§15, finding 8). Its absence test is
`facts.name == nil and facts.questLevel == 0 and facts.requiredLevel == 0`
(`:302`), and every one of those three is also what a failed read produces: `scalar`
returns its default of 0, and `name` is nil whenever `nameKind ~= PLAIN`. So the test
cannot tell an unknown quest from an unreadable one.

```
# post: false is cached only when the name read ANSWERED -- ClientRead.Call returned
#       PLAIN, or returned a genuine nil from a call that did not raise -- and the
#       scalars agree the quest is absent. When the name read did not answer, nil is
#       returned, NOTHING is cached, and readFailed is bumped
# raises: never
function quest_facts(questId: integer) -> QuestFacts?
```

- **`readFailed` is a new counter** under `questieBridge`, so a recurrence is visible in
  `/pa quests` instead of looking like missing data.
- **Why no harness check caught it:** `tests17.lua`'s Q5 proves a raising getter yields
  `Errored` at the *state* level, and nothing exercised a getter that raises for one
  quest while the bridge stays `Available`. Checks T9–T12 in §11.1 are those cases.

  is drawn with a black outline, so it stays legible against a bright nameplate at the

  source. Doing it properly means this addon drawing its own tooltip, which is a
  feature rather than a setting.
- **Known exceptions.** Unchanged. This phase adds none: nothing new is hooked.

## 10. Rule compliance

| Rule | How Phase 18 meets it |
|---|---|
| 1. Blizzard's Lua never calls ours inline | §2 and §3 run from Nameplates' and QuestMarkers' existing paths. No dropdowns — §3's position is two sliders for exactly this reason |
| 2. Never write into Blizzard's variables or tables | §2 writes a font on our own font string; §3 anchors our own frame. **No CVar is written at all**, because §4 does not ship |

## Assumptions

- **The guild outline is wanted at every size,** including 6 points where it is heaviest
  relative to the glyphs. D3 made it unconditional; if 6-point text looks bad outlined,
  the fix is a higher minimum rather than a new switch.
- **`"OUTLINE"` is accepted by this client's `SetFont`.** Not provable offline —
  `TBFFlags` has no definition in the export — so §11.3 step 1 checks it and the
  fallback makes a wrong guess visible rather than broken.
- **Moving the marker's default is not a regression for anyone.** It has been above the
  bar for a day. Unlike rev 1, this is not accompanied by a claim that the old placement
  is still reachable: it is not (§3.1).
- **Deleting `Spikes/` loses nothing.** Phase 16's and Phase 17's questions are answered
  and recorded in those documents, and SQ2 is answerable from `/pa quests` in ordinary
  play (§11.4).
- **`PersonalAddonSpikeLog` is left declared for one version.** An existing saved log is
  not orphaned mid-upgrade; it goes in Phase 19.
- **§4's two routes are the only two.** A third — asking Blizzard to pass the nameplate
  as `SetWorldCursor`'s `parent` — is not available to an addon, since the client raises
  that event itself.
