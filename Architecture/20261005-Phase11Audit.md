1. 5.4 (and 1.4) | Undefined reference | Section 5.4's `render_rows` contract takes a `settings: ThreatPanelSettings` argument, but `ThreatPanelSettings` is never defined in the Types section (§1.4) or anywhere else in the document. | Define `ThreatPanelSettings` in Section 1.4.
2. 5.4 (and 1.4) | Contradiction | Section 5.4 states the target marker compares `C_NamePlate.GetNamePlateForUnit("target")` with "the row's own plate, by frame identity". However, the `MobRow` structure defined in §1.4 only contains the string `token`, not a reference to the `NamePlateFrame`. The design does not provide a way for `render_rows` to access the plate frame without an undocumented client lookup. | Add a `plate: NamePlateFrame` field to `MobRow` populated during `collect_rows`, or specify that `render_rows` dynamically calls `C_NamePlate.GetNamePlateForUnit(row.token)`.
3. 5.2 (and 5.5) | Lifecycle leak | Section 5.2 relies on an "eighth sweep" garbage collection to drop orphaned tokens for units that disappeared without a `NAME_PLATE_UNIT_REMOVED` event. However, Section 5.5 states the panel is "Idle" with "no ticker" (and thus no sweeps) while out of combat. If the player spends a long time out of combat, orphaned tokens will accumulate indefinitely in the `tokens` set, leaking state and potentially causing a massive lag spike when combat starts and `collect_rows` iterates them. | Clear the `tokens` set when combat ends and rebuild it via `C_NamePlate.GetNamePlates()` when combat starts, or keep a slow ticker active out of combat to run the garbage collection.
4. 4.2 (and 5.4) | Lifecycle leak | Section 5.4 states the panel reuses rows from a pool of 16. Section 4.2 states that when a client function returns a readable nil (e.g., `UnitName` for an unknown unit), `ClientRead.Pass` returns `Absent` and does not call the widget setter. Because the setter is skipped, the reused row will leak state by continuing to display the name or health of the previous mob it represented. | Specify in §5.4 that `render_rows` must explicitly clear the text and reset the status bar to zero for any field where `pass` returns `Absent` or `Unavailable`.
5. 5.5 (and 5.2) | Missing branch | Section 5.5 claims that enabling the feature in combat "starts at once". However, Section 5.2 states that nameplate tokens only come from `NAME_PLATE_UNIT_ADDED` events. If the feature is enabled dynamically via `/pa on` during combat, those events have already fired, meaning the `tokens` set will be empty and existing mobs will not appear on the panel until their plates are removed and re-added. | Specify that the feature must populate its initial `tokens` set by calling `C_NamePlate.GetNamePlates()` during its enable routine.
